# Legado_Max 项目开发

## 目标

在 Legado_Max 中做可追溯、范围受控、与现有架构一致的变更。仓库当前代码、构建文件、测试和相邻实现始终是事实源；本技能负责规定调查、实施与验证方式，不替代实时核验。

## 开始前

1. 阅读当前会话和仓库中的项目指令，确认用户要求、禁止事项与验收标准。
2. 查看工作区状态和已有差异，区分用户改动与本次任务；不得覆盖或顺手整理无关内容。
3. 明确影响面：入口、调用链、状态、持久化、线程、权限、外部接口、生成资产和构建变体。
4. 结构发现优先使用代码知识图谱；仅在查询字符串、配置、脚本或图谱信息不足时回退到文本搜索。
5. 先读[项目地图](references/project-map.md)，再读任务命中的专项引用和邻近生产代码、测试。

## 工作方式

### 功能或行为变更

1. 先加载 `brainstorming`，澄清行为、边界和验收条件。
2. 加载 `test-driven-development`，先写能失败的最小测试并确认 RED。
3. 写最少实现使测试 GREEN，再在持续通过的前提下重构。
4. 不新增用户未要求的功能，不借机迁移无关架构。

### Bug 修复

1. 先加载 `systematic-debugging`，复现并定位根因，不凭症状猜补丁。
2. 加载 `test-driven-development`，把复现固化为失败测试。
3. 做最小修复，并验证失败测试转绿及相关回归。

### 审查或诊断

默认只读调查。以可复核的文件、符号、调用链或命令输出为证据；除非用户明确要求修复，否则不编辑文件。

### 完成前

加载 `verification-before-completion`，执行[验证与交付](references/verification.md)。不得用“应该通过”代替刚运行的结果。

## 调查与实施循环

### 1. 定义可观察结果

- 把用户描述转成可以验证的行为、输入、输出和失败模式。
- 区分必须完成、明确不做和需要授权的事项。
- 确认目标用户、设备/系统范围、数据兼容性和受影响 variant。
- 对修复任务记录稳定复现步骤；对重构记录必须保持不变的外部行为。

### 2. 建立证据链

- 从入口追踪到实现、持久化或外部边界，再追踪关键调用方。
- 读取当前测试，确认它们实际执行哪些生产路径，而不只看测试名称。
- 对配置和脚本同时核对定义处与消费处，避免只改一端。
- 把观察事实、推断和待验证假设分开记录。

### 3. 控制变更范围

- 先选能满足验收条件的最小切片，并明确不在本次处理的相邻问题。
- 一次只改变一个可验证行为，保持 RED→GREEN 的因果关系清晰。
- 公共 API 或全局基类变更前，先列出直接消费者和兼容策略。
- 生成文件必须由明确来源生成，不手工混改源文件与产物。

### 4. 分层验证

- 先运行最靠近行为的测试，再运行受影响目标的编译或构建。
- 数据、安全、UI 和网络边界按专项引用增加 instrumentation、集成或运行时验证。
- 验证失败时先定位根因；不得删除测试、放宽断言或关闭安全机制换取绿色结果。
- 环境阻塞时保留失败证据，继续能安全完成的静态核验，并准确标注边界。

## 实施原则

### 事实与邻近范式优先

- 在写代码前读取目标符号定义、直接调用方、已有测试和同目录相似实现。
- 版本、flavor、Gradle task、API 和目录可能变化，使用前从仓库重新核验。
- 复用现有抽象与依赖；若现有模式互相冲突，记录证据并选择与目标功能最近、仍在维护的模式。
- 示例只能来自仓库真实 API；不要发明单例、基类、适配器或构建命令。

### 风险决定验证深度

以下区域是高风险边界，不是绝对禁改区：

- `base` 基类、全局状态和跨页面事件；
- `AppDatabase`、schema、迁移及用户数据；
- 书源/规则引擎、Rhino 执行和网络请求；
- HttpServer、WebSocket、路由、上传、备份、认证和 CORS；
- 发布构建、依赖、混淆、签名和内嵌 Web 资产。

确需修改时，先解释影响面，保持兼容性，补足针对性测试，并扩大到受影响调用方、变体或运行时验证。

### 边界与安全

- 未经用户批准，不新增依赖、不更换技术栈、不做无关 schema 迁移或架构重写。
- 不删除迁移历史，不用破坏性回退掩盖迁移缺失，不伪造测试通过。
- 不把 secret、token、密码或隐私数据写入客户端、日志、错误信息、截图或文档。
- 不吞掉协程取消，不让后台层直接驱动 Toast、导航或分享等 UI 副作用。
- 需求若需要凭据、破坏性数据操作、发布权限或范围扩张，停止并向用户说明所需授权。

### Git 纪律

- 开始和结束都检查状态与差异，只处理本次范围内的文件。
- 未经用户明确授权，不执行 stage、commit、push、发布或创建 PR。
- 即使项目中的其他说明鼓励自动提交，本条对本技能的任务仍要求先取得用户授权。

## 完成标准

只有同时满足以下条件才能声称完成：

1. 用户要求逐项对应到实现或明确的未完成项。
2. 相关测试先证明能捕获问题，再证明修复有效；不适用 TDD 时说明原因。
3. 已运行与风险匹配的最小测试、目标编译和必要的扩大验证。
4. 已检查最终差异，无用户改动丢失、无无关文件、无秘密或生成物误入。
5. 交付报告列出实际命令、退出结果、覆盖内容、跳过项及原因。
6. 静态检查、编译、构建、instrumentation 和运行时验证的边界分别陈述，不互相冒充。

## 常见失误

- 只读文档，不核对当前实现和任务列表。
- 把高风险误写成“禁止修改”，导致真正需求无法完成。
- 把 `viewModelScope.launch`、Compose 或手动迁移一概禁止。
- 为了通过构建删除迁移、关闭鉴权、放宽 CORS 或加入破坏性 fallback。
- 假设 `modules/web` 属于 Gradle，或假设本地 `pnpm build` 已同步 Android assets。
- 只跑编译就声称数据库迁移、安全、设备行为或所有变体通过。
- 自动提交或推送用户尚未审阅的改动。

遇到不确定性时，优先继续做安全、只读、范围内的核验；只有缺少的选择会实质改变结果时才请求用户决策。
